What ebb-ai does

Most agent code today calls LLM APIs synchronously the moment the call happens. ebb-ai sits in front of that call and answers a single question: does it have to run right now? If the agent says by tomorrow morning is fine, ebb-ai picks the cleanest window inside that deadline — on the local electricity grid, at the LLM provider's cheapest tier, on whichever route makes the most sense — and dispatches there. It returns the result with a per-task carbon receipt you can audit.

Concrete example

You ask the agent to summarize 50 GitHub issues by 9 a.m. tomorrow. ebb-ai sees you're in US-CAL-CISO, forecasts the next 24h, picks the 03:00 a.m. window (120 gCO₂/kWh), dispatches via Anthropic's Batch API (50% off, within 24h SLA), and writes a receipt: 50 calls executed at 120 gCO₂/kWh ≈ 0.9 g CO₂e total, cost $0.42 instead of $0.84. The summary lands in your inbox by 6 a.m.

Why it matters

  • Carbon. US grid intensity varies 30–60% within a single day. Inference at 2 p.m. on a hot day is materially dirtier than the same call at 3 a.m. AI inference is, by volume, already a larger workload than training in aggregate.
  • Dollars. Anthropic and OpenAI both ship Batch APIs at a flat 50% discount for tasks that can wait up to 24 hours. Almost no agent code uses them by default.
  • Latency, honestly. Off-peak sync execution is sometimes faster because providers throttle and queue at peak. The Batch API is not faster — it trades latency (up to 24h SLA) for the 50% discount. Carbon and dollars are the pitch; latency is a third-tier side effect.

The gap is at the agent / MCP layer. There are mature carbon-aware tools upstream (Microsoft Carbon Aware SDK, Electricity Maps, WattTime, GridStatus) and downstream (Batch APIs). Nothing stitches them together for agents. ebb-ai does.

Install

Three paths, by how close to your agent you want ebb-ai to live.

1

As a library (TypeScript)

For agents you control end-to-end.

pnpm add @ebb-ai/core

// then in your agent
import { defer } from "@ebb-ai/core";

const result = await defer(
  () => anthropic.messages.create({ /* ... */ }),
  { deadline: "2026-05-13T08:00:00-04:00",
    region: "US-CAL-CISO" },
);
2

As an MCP server (zero-code)

For Claude Desktop, Claude Code, OpenClaw, Codex, any MCP-aware agent.

git clone https://github.com/Vitalini/ebb-ai.git
cd ebb-ai
pnpm install
pnpm build

# Claude Code
claude mcp add ebb-ai -- \
  node $(pwd)/packages/mcp-server/dist/server.js

# or edit your Claude Desktop / OpenClaw / Codex config —
# see examples/ for ready-to-paste snippets.
3

As a library (Python)

For agents in the Python ecosystem.

pip install ebb-ai[anthropic,openai]

# then in your agent
from ebb_ai import defer

result = await defer(
    task=lambda: client.messages.create(...),
    deadline="2026-05-13T08:00:00-04:00",
    region="US-CAL-CISO",
)

Requirements: Node 20+ and pnpm 9+ for the TypeScript packages; Python 3.11+ for the Python package. Apache-2.0. No analytics, no telemetry, no required API keys (Electricity Maps optional, falls back to a deterministic mock so the whole stack runs end-to-end without configuration).

What you actually see

A 60-second walkthrough of the MCP server inside Claude Code.

1
You: "Summarize these three GitHub issues, but wait until off-peak — I don't need it until breakfast."
2
Claude Code calls get_grid_forecast(region="US-CAL-CISO", hours=12) via the ebb-ai MCP server. Sees 03:00 is the cleanest hour at 120 gCO₂/kWh.
3
Claude Code calls schedule_task(prompt="Summarize…", deadline="…08:00", region="US-CAL-CISO") → gets back a task_id.
4
Reply to you: "Queued. Will run around 03:00 tonight via Anthropic Batch API; the summary receipt will be in your queue by 06:00. Estimated 4 g CO₂e total instead of ~12 g at peak."
5
You at breakfast: open the dashboard, see the summary plus a per-task carbon receipt: ran 03:42, region US-CAL-CISO, intensity 118 gCO₂/kWh, tokens in / out, dollar cost saved.

Standards work

ebb-ai's longer-term thesis is that deferrability belongs in the Model Context Protocol itself. We've drafted an upstream proposal to add three optional fields to the tools/call request envelope: 

{
  "_meta": {
    "priority": "background",            // "interactive" | "background" | "now"
    "deadline": "2026-05-13T08:00:00-04:00",
    "carbon_budget_g": 5
  }
}

Servers that ignore these fields keep working unchanged. Servers that honor them gain a clean way to queue, batch, or defer, and to return a carbon receipt on the eventual CallToolResult. Reference implementation lives in this project; spec engagement is open on modelcontextprotocol/specification.
